# 6개 맵의 3D 준비·표시 진도 동기화

## 확인한 원인

1. 서버 물리 환경 생성과 브라우저의 실제3D 장면 준비를 같은 것으로 취급했다.3D 로딩이 늦은VO도 서버에서는 이동할 수 있었다.
2.2D 실행 도중3D로 전환할 때 물리 실행을 먼저 멈추지 않아 로딩 시간 동안 진행했다.
3. HTTP 터널은 최대128개 바이너리 메시지를 Base64/JSON으로 변환한 뒤 한 응답에 모두 비웠다. 느린 브라우저에서 큰 버스트·변환 비용·재접속이 발생할 수 있었다.
4. 브라우저로 보내는 카메라/제어 메시지는 HTTP 요청을 하나씩 대기시켜 전송했다. 입력이 빠르면 대기열이 커졌다.
5. 생산자인 물리 계산이 소비자인 화면의 실제 처리 진도를 확인하지 않았다. 화면이 잠시 바쁘면 중간 대신 나중 상태를 보게 될 수 있었다.

## 변경

- 시작 화면에서 **3D · 첫 장면부터 보기**를 선택할 수 있다. 세 장면 모두 준비되기 전에는 세 로봇을 이동시키지 않는다.
- 단순 iframe load/canvas 존재가 아니라 Viser의16×16 실제 렌더 응답으로 첫 장면 준비를 확인한다. 메시/박스는 기존 원시 메시 지오메트리를 사용한다.
-2D↔3D 전환은 실행 중인 로봇을 우선 멈추고 표시를 전환한다. 준비가 끝나면 기존 실행 상태였던 경우 함께 재개한다.
- 첫 준비 이후에는 매 프레임 별도 이미지 캡처를 반복하지 않는다. Viser 원본 메시지의 순서가 보장된 자세 업데이트 뒤에 프레임 마커를 보내고, iframe의 원본 메시지 처리와3회 애니메이션 프레임 후에 표시 확인을 반환한다.
- 부모 대시보드도 DOM 표시 후에 공통 표시 프레임을 알린다. 부모/3D 처리 진도보다6물리 프레임 이상 앞서면 계산을 기다린다. 느린 환경에서는 벽시계상의 재생 속도가 느려지며 물리 dt/충돌 판정/시드 조건은 바뀌지 않는다.
- 재생 기록도 같은 표시 진도를 따른다. Seek/Reset은 확인 세대를 바꿔 과거 확인 메시지가 새 장면을 해제하지 못하도록 한다.
- 터널은 길이 헤더를 둔 바이너리 배치로 전환했다. Base64 변환을 제거하고 한 poll은 최대4패킷·약512KB로 제한한다(단일 큰 패킷은 분할하지 않는다).
- 수신 큐는8패킷으로 제한하며 가득 차도 정상 메시지를 버리거나5초 후 강제 재접속하지 않고 소비를 기다린다. Native Viser 메시지는 순서를 유지한다.
- 클라이언트의 송신은 묶음 처리하며 실제 bufferedAmount를 기록한다. 큐가 비정상적으로 초과하면 조용히 버리지 않고 연결 오류/표시 대기로 전환한다.
- 기존 JSON/단일 메시지 터널도 협상하여 호환한다. 기존 원본 결과·Pygame 자료와 회피/물리 방정식은 유지한다.

## 검증

관련 pytest63개 통과·0실패, 의존성 경고12개. 실제 UI 경로 메서드의 Node 검사4개도 통과했다. 전체 연구 실험/테스트 스위트를 재실행했다는 의미가 아니다.

실제 Chromium에서 Map1~Map6, Naive·VO·ORCA18개 라이브3D 세션의 준비·프레임 진행·정지·Canvas를 확인했다. Map2 VO HTML 로딩을2초 지연한 동안 생성된 세 로봇은0프레임에 머물렀다. 부모 화면을1초간 의도적으로 막은 검사에서 계산은 표시 확인보다 최대6프레임 앞에서 기다렸다. 실제 표시 시각의 연속 갱신 간격은 물리 시간0.2초 이내였다. 바이너리 poll 및 구간별 실제 렌더 확인도 검사했다.

실패한 개발 중 검증에서는 표시 확인이 오지 않으면6프레임에서 정지하는 보호 동작이 확인되었다. 매 프레임 이미지 캡처의 비용을 제거하고 Viser 원본 메시지/애니메이션 확인으로 바꾼 후 최종6맵 검사를 통과했다. 테스트에서 지연 주입 URL을 잘못 매칭하던 부분도 파일의 실제 설정을 기준으로 수정했다.

최종 원본 검증/로그/6개 스크린샷: results/newton/validation/presentation_08849a66/. 이는 시작과 중간 표시 검증이며 각 조건의 목적지 도달 실험을 새로18회 완료했다는 뜻은 아니다.

## 사용

기존 동시 비교를 종료하고 새로고침한다. 시작 화면을 **3D · 첫 장면부터 보기**로 선택한 뒤 Start를 누른다. 준비 중에는 각 카드의 안내와 준비 수를 확인할 수 있다. 화면의 GPU 처리 속도가 한계인 경우 속도를 보장하거나 프레임을 건너뛰는 대신 계산이 표시를 기다린다.
